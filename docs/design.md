# 本地数据子系统 · 设计总纲（单文件合并版）

> **适用**：macOS 原生 Swift App + 自带 Node 运行时的 sidecar + 从「纯 JSON 全量文件」迁移。
> **本文件是唯一权威版本**，合并自此前的《本地数据层》《Nodestore 方案》《自研存储引擎》三份草稿与运行时自检脚本。
> 草稿里的修订史已折叠，只保留当前结论；凡与本文件冲突的旧表述，一律作废。
>
> **生成日期**：2026-10-30　**状态**：架构已收敛，实现未开始（0 行存储代码）
> **实测环境**：Node v22.22.2 / V8 12.4 / macOS 26 / **x64**。换到 Apple Silicon 数值会更好看，但**比例关系不变**（因为瓶颈在内核与序列化，不在 CPU）。

## 0. 一页速览

### 0.1 一句话总纲

**sidecar 是唯一写者；三类数据用三种存法；热数据在内存；IPC 只传命令与失效信号，不传数据。**

### 0.2 七条决定（后文所有细节都服务于这七条）

| # | 决定 | 理由 | 章节 |
|---|---|---|---|
| D1 | **sidecar 唯一读写者**，Swift 不直连数据文件 | 单写者把「跨进程一致性」整类删除；热数据可放心进内存 | §2 |
| D2 | **三类数据三种存法**：业务 / 抓包 / agent 各用专属结构 | 可变性与体积差两个数量级，硬塞进同一引擎必有一类被牺牲 | §4 §5 §7 |
| D3 | **不引入 SQLite**，业务数据自研 CoW 页 + 位图索引 | 筛选器由业务写死 → 不需要 B-tree + 查询优化器 | §4 |
| D4 | **抓包与 mock 是两个命名空间**，独立生命周期与独立 seq | 「清空全部」与「删单条」是互斥语义，不能共用一个结构 | §5.5 §6 |
| D5 | **内核统一**：IO 薄层 + Buffer Pool + group commit + 四层缓存 | 四个后端共享；收益几乎全部来自把 fsync 从 20 ms 摊薄 | §3 |
| D6 | **调用方不 parse 大 body**，只交 `path / off / len` | 300 KB 文档读盘 0.27 ms、`JSON.parse` 1.68 ms，贵 6 倍 | §1.3 · §9.4 |
| D7 | **自带 Node 运行时**，钉 24 LTS，启动按「能力」而非「版本号」自检 | 依赖系统 node 在 macOS 上不是低概率，是必然失败 | §10 |
| D8 | **可读性用工具买，不靠格式**：随包发布 `store dump/cat/check/export` | 二进制格式是性能的代价；没有工具的可读性是 0，而 SQLite 的可读性同样来自工具 | §16 |
| D9 | **落盘单一文件 `store.db`**：内部是区段表 + 段序列，不是目录树 | 读性能无损（pread 只认 offset）、备份免费（clone ≈0）；代价是空间回收变最终一致、可读性只能靠工具 | §15 |

### 0.3 三类数据地图

| 数据 | 形态 | 存法 | 规模假设（**尚未被真实数据验证**） | 章节 |
|---|---|---|---|---|
| 业务数据 | 固定字段、可变、要过滤 | CoW 页文件 + 位图索引 + 定长 snapshot | 十万行级 | §4 |
| 抓包 | 固定元数据 + 大 body，只追加 | 按会话分组段 + 按列分段 + 内容寻址 body | 每天 1 万条 / body 约 200 MB | §5 |
| mock | 少量、可变、需单条删 | 内存主存 + tombstone journal | 千条级 | §6 |
| agent 结果 | 字段不固定，run 结束即封 | shell 索引 + body 独立文件 | 单 run 100 KB–5 MB | §7 |

### 0.4 现在能拿它做什么

- 能用：作为实现依据（每章都有文件布局、参数、伪码、实现量估计）。
- 不能当：性能承诺（所有数字是**微基准**，没有一次端到端真实负载）、完备设计（见 §14 的 3 个未闭环 + 4 个空白）。

### 0.5 建议的第一步

**不要先写存储引擎。** 先做 §3.8 的 P1 + P2（IO 薄层 + Buffer Pool + Committer，约 650 行），
把现有的 `writeFileSync` 换成「进 buffer pool + group commit」。不改任何数据结构，就能把
「10k 条 50 ms/次」压成「一个窗口 20 ms」。这是全项目性价比最高的一次验证。

## 1. 为什么必须换：实测基线

### 1.1 现状模型：每次保存 = 读全量 + 解析 + 改 + 序列化 + 写全量

| 记录数 | 文件大小 | parse | stringify | 写盘 | 读盘 | **单次全量落盘** |
|---:|---:|---:|---:|---:|---:|---:|
| 2,000 | 0.5 MB | 2.4 ms | 4.5 ms | 2.1 ms | 1.9 ms | **11 ms** |
| 10,000 | 2.8 MB | 11.5 ms | 24.8 ms | 7.3 ms | 6.5 ms | **50 ms** |
| 50,000 | 13.9 MB | 73.2 ms | 114.5 ms | 34.0 ms | 58.8 ms | **281 ms** |
| 200,000 | 55.7 MB | 281.2 ms | 372.9 ms | 134.2 ms | 212.1 ms | **1000 ms** |

两条可以直接用的结论：

1. **`stringify` 比 `parse` 贵 1.3–1.6 倍**，也就是说**写比读先死**。
2. 10k 条（3 MB）已经 50 ms/次 —— 在主线程上这就是卡顿；50k 条开始肉眼可见；200k 条等于每次保存卡 1 秒。

### 1.2 对照：真数据库在同样 20 万条上的表现

| 操作 | 耗时 |
|---|---:|
| 单条写入（独立事务） | 0.48 ms |
| 100 条批量（单事务） | 0.59 ms（摊销 6 µs/条） |
| 主键点查 | 7 µs |
| `ORDER BY 未索引列 LIMIT 50` | **27 ms/次** ← 反例：索引设计的权重远大于引擎选型 |

这张表是**放弃 JSON 的依据**，不是「改用 SQLite」的依据。为什么不直接用 SQLite，见 §4.1 与 §4.6。

### 1.3 但真正的瓶颈不在存储引擎：它在序列化边界

| 文档尺寸 | 从磁盘读 bytes | `JSON.parse` | 倍数 |
|---:|---:|---:|---:|
| 20 KB | 0.03 ms | 0.07 ms | 2× |
| 300 KB | **0.27 ms** | **1.68 ms** | **6×** |
| 1 MB | 0.36 ms | 3.32 ms | 9× |
| 3 MB | 1.01 ms | **9.75 ms** | **10×** |

**读一个 3 MB 的 agent run，磁盘只要 1 ms，`JSON.parse` 要 10 ms。** 这个差距随尺寸线性扩大。

所以「读写要极致」的全部空间里，最大的一块不是「换个更快的引擎」，而是**别让任何人碰那份 JSON**（D6）。
`fsync` 是另一块：一次 20 ms，比一次 `write` 贵 2400 倍（§3.1）。

### 1.4 从这张基线推出的三条硬规则

1. **不可变的大对象不要进引擎**，它是文件，只需要有人别解析它。
2. **可变的小数据要进内存**，磁盘只负责持久化与快照。
3. **写的上限由 fsync 频率决定**，不由引擎决定 —— 所以必须有 group commit。

## 2. 架构：单写者 + 三类数据 + 统一内核

### 2.1 进程与数据通路

```
┌──────────────────────────────┐
│ Swift App（只有 UI 与渲染）    │
│  列表 / 详情 / 编辑            │
└───────────┬──────────────────┘
            │ ① 命令（写）：{op_id, id, expect_rev, patch} → {seq, rev}
            │ ② 查询（读）：分页 + 字段裁剪 + cursor
            │ ③ 订阅：push {ns, seq, ops:[{e,id,op,rev}]}  ← 只带 id，不带内容
            │ ④ 大 body：只交 {file, off, len}，Swift 自己读盘
┌───────────▼──────────────────┐
│ Node sidecar（唯一写者）        │
│  ┌────────────────────────┐  │
│  │ 门面 API + seq/订阅      │  │
│  ├────────────────────────┤  │
│  │ 内核：IO 薄层 / Buffer Pool │
│  │      / Committer / 缓存   │  │
│  ├───────┬───────┬────────┤  │
│  │ biz   │capture│ mock   │  │
│  │ CoW页  │会话分段│ 内存+日志│  │
│  ├───────┴───────┴────────┤  │
│  │ agent：shell 索引 + body 文件│
│  └────────────────────────┘  │
└───────────┬──────────────────┘
            │ 直接 file IO（不走 IPC）
      ┌─────▼──────────────────┐
      │ ~/Library/Application Support/<BundleID>/
      │   store.db  ← 一个文件，内部是区段表 + 段序列（§15）
      └────────────────────────┘
```

**读路径为什么不过 IPC**：业务数据全驻内存（几万行 × 200 B ≈ 10 MB），一次查询是位图位与 ≈ 3 µs；
抓包查询是「读 1–2 个列区 + 顺序扫」≈ 1–2 ms；agent 文档是 offset 交接，Swift 自己读。
这三种都不需要把数据搬过管道。

### 2.2 五条不变量（任何实现都必须满足）

1. **单写者**：同一时刻只有一个进程、一个提交点在写。
2. **read-your-writes**：`commit` 返回后，读立刻可见。
3. **崩溃安全**：`kill -9` 不丢已 ack 的事务、不损坏文件；掉电最多丢一个提交窗口。
4. **失效可传播**：每个命名空间一个单调 `seq`，客户端断线可从 `since` 补齐。
5. **协议可演进**：信封带 `v`，未知字段忽略；磁盘格式带 `ver`。

### 2.3 落盘布局：一个文件

```
~/Library/Application Support/<BundleID>/
├── store.db                  全部数据（见 §15 的内部结构）
├── backups/20261030T2300.db  时点快照（APFS clone，几乎不占空间）
└── legacy/notes.json         旧数据，切换后只读保留
```

`store.db` 内部（不是目录，是区段序列）：

```
[0,4K)      文件头   magic "NSTORE" + u16 format_ver + u16 seg_size
[4K,8K)     meta.a   区段表 + 各家族 seq 水位，带 CRC32
[8K,12K)    meta.b   同上，交替写入（原子切换）
[12K,...)   段序列   每段 16 MB，段头 64 B 自描述
                     {magic, ver, type, rows, len, crc32, session_id}
```

`type` 四类：`biz_page` / `cap_meta`（会话的列区）/ `cap_body` / `run_doc`。

**两条不可违反的布局规则**
- **大 body 与热数据必须分在不同段**：段是回收与缓存的最小单位，混在一起会让清空和 buffer 管理都退化成逐字节判断。
- **清空单位必须是「段组」**：一个会话对应一组段，清空 = 标记这一组 dead（§5.5）。绝不允许按行删除来实现清空。

> 完整的内部结构、清空机制与空间回收语义，见 §15。

## 3. 内核：IO / 缓冲池 / 提交 / 缓存 / 失效

> 前文给了四种存储结构，本章是它们共用的那一层。
> 准确说法：**这层内核复用了数据库的内核，但不做通用查询引擎。**

### 3.1 IO 三条铁律（本机实测）

| 操作 | 实测 |
|---|---:|
| `write` 4 KB（进 page cache，不刷盘） | **8.3 µs** |
| `fsync`（有数据 / 空提交，一样贵） | **约 20 ms** |
| 读 4 MB（page cache 命中） | 1.81 ms ≈ 2.2 GB/s |
| 顺序写 64 MB @ 1 MB 块 | 763 MB/s |
| 顺序写 64 MB @ 64 KB 块 | 400 MB/s |
| 顺序写 64 MB @ **4 KB 块** | **206 MB/s** |
| `open`+`close` × 13（一个 chunk 的全部列） | 306 µs |
| 扫 100 万行 u32 列 + 过滤（TypedArray 视图） | 3.67 ms（其中 IO 1.81） |
| 同上，改用 `buf.readUInt32LE(i*4)` | 计算部分 4.60 ms（**慢 2.4 倍**） |

**铁律零：CRC 一定用原生，别自己写。**
写路径上唯一的纯 CPU 热点是 CRC32。表驱动 JS 只有 **332 MB/s**（16 MB 要 48 ms），
而 Node 内置的 `zlib.crc32` 是 **2812 MB/s**（5.7 ms），**8.5 倍**，且支持增量拼接。
这不是「JS 慢」，是「库的选择」—— 同理 zstd 也直接用原生（与 Rust 用的是同一个 libzstd）。
> `zlib.crc32` 是 Node 22.2+ 才有；更早版本退回表驱动，或把 CRC 丢给 worker。

**铁律一：写几乎免费，fsync 才贵。**

```
吞吐(条/秒) = 每批条数 / max(提交窗口, fsync 延迟)
```

8.3 µs 对 20 ms，差 2400 倍。逐条 fsync 最高只有 **50 次/秒** —— 抓包每秒几十条、
业务数据一次导入几万条，逐条提交不是「慢」，是**完全不可用**。
（20 ms 偏高可能因为这台机器的磁盘或虚拟化；即便换成 0.5 ms 的 NVMe，结论不变：**永不逐条提交**。）

**铁律二：写块必须 ≥ 64 KB。** 4 KB 块只有 1 MB 块的 27% 吞吐，差的全是 syscall 开销（53k/s 对 1k/s）。

**铁律三：fd 要少 —— 单文件方案把这条直接消掉了。**
旧的多文件方案里，开一个文件 20 µs，一个 chunk 的 13 个列文件 = **306 µs**，比你查 1000 行（0.1 ms）还贵 3 倍，所以必须做 fd LRU 池。
改成单文件（§15）后全库只有 **1 个 fd**，这笔开销归零 —— 这是单文件方案顺带赚到的。

### 3.2 mmap 还是 pread：选 pread

| | mmap | **pread（本项目选它）** |
|---|---|---|
| 小读 | 快（无 syscall） | 有 syscall |
| 顺序大扫 | 快 | 快（内核预读） |
| 大文件随机读 | 冲刷 page cache | 可控 |
| Node 支持 | ❌ 无内置 | ✅ |
| 崩溃安全 | 文件被截断后访问映射 → SIGBUS | 返回 EOF |

**Node 没有 mmap，也不必为此写 native addon**：`pread` + TypedArray 视图读 8 MB 列只要 1.8 ms。
只有 Swift 侧读超大 body 时才考虑 mmap。

### 3.3 列扫描必须用 TypedArray 视图

```js
const buf = readExact(fd, off, rows * 4);                      // 一次 pread
const col = new Uint32Array(buf.buffer, buf.byteOffset, rows);  // 零拷贝视图
let hit = 0;
for (let i = 0; i < rows; i++) if (col[i] >= 50000) hit++;
```

比 `buf.readUInt32LE(i*4)` 快 2.4 倍（4.60 → 1.92 ms / 百万行）。更值钱的是第二点：
**`ArrayBuffer` 属于 external memory，不进 V8 heap**，大列扫描不产生 JS 对象 → 不触发 GC 停顿。
这是「极致性能」在 GC 层面唯一的实招。

推论：**对象缓存必须按条数限容，不能按字节**，因为缓存里的 JS 对象是进 heap 的。

### 3.4 Buffer Pool：为「写合并」而生，不为读缓存

先问一句：OS page cache 已经缓存了文件页，为什么还要自己搞一层？

因为 OS page cache 有三个你控制不了的缺陷：
1. **不可控淘汰** —— 没法告诉内核「这 64 MB 别丢」，一次全量导出就把热数据冲掉。
2. **无法合并小写** —— 100 次 4 KB `write` 不保证合并，而 4 KB 与 1 MB 差 3.7 倍。
3. **无法固定与预取** —— 不能 pin 索引页，也不能预取下次要用的列。

所以这一层的职责很窄：**脏页合并 + 热点固定**。

```
page      = 64 KB          （不是 4 KB：实测 4 KB 写只有 1 MB 写的 27% 吞吐）
frames    = 1024           （64 MB）
分区       = biz 40 MB / capture 16 MB / mock 4 MB / agent 4 MB
脏表       = Map<pageId, {store, dirtyBytes, firstDirtyAt}>
flush 触发 = 脏字节 ≥ 4 MB 或 最老脏页 > 200 ms（先到先触发）
flush 动作 = 按 store 分组，同 store 内相邻页合并 writev，单次上限 1 MB
eviction  = CLOCK（不用 LRU-K，复杂度不值）
不做      = 多版本 / 页级锁（单写者）/ doublewrite（CoW 自带）
```

### 3.5 提交协调：整个进程只有一个地方调 fsync

单写者最大的好处在这里兑现：

```
写请求 → 进对应 store 的 buffer pool（8.3 µs，立即回「已接收」）
      ↓
Committer 收集同一窗口内所有 store 的脏页
      ↓
① 各 store 各自 append 到自己的 journal（顺序写，不 fsync）
② 写一条 commit record：本轮覆盖的 store 列表 + 各自 seq 水位
③ 一次 fsync —— 本轮所有 journal 一起刷
④ 更新内存可见水位 → push {ns, seq}
⑤ 回 ack
```

`N` 个 20 ms 合并成 1 个 20 ms。N=1000 时约 **5 万条/秒**。

**窗口必须自适应**，否则会雪崩：

```js
window = clamp(2 * ewma(fsyncLatency), 8, 100)   // ms
```

固定 16 ms 而 fsync 要 20 ms 时，提交队列会持续堆积，延迟越滚越大。

**四类数据用四种持久性 —— 这是本章最该抄的一张表**

| 数据 | 提交时机 | 崩溃最多丢 | fsync 频率 |
|---|---|---|---|
| 业务数据 | 每次写（走 group commit） | 一个窗口（≤ 100 ms） | 每轮 1 次 |
| 抓包 | chunk 封口 或 每 2 s | 2 s 内的记录 | 低频 |
| mock | 每次写 journal，**不 fsync** | 几条（重放补） | 仅 snapshot |
| agent 文档 | run 结束 1 次 | 整个 run（本来就没意义） | 每 run 1 次 |

抓包若每条 fsync：一天 10 万条 × 20 ms = **2000 秒纯 fsync**。这个差异化比任何存储结构优化都值钱。

### 3.6 缓存四层与唯一一条失效规则

| 层 | 缓存什么 | 容量 | 命中延迟 | 谁失效 |
|---|---|---|---:|---|
| OS page cache | 文件页 | 系统自动（可达数 GB） | ~2 µs | 内核 |
| Buffer Pool | 脏页 + 热点页 | 64 MB | ~1 µs | 按 store 分区 |
| 对象缓存 | 解析后的行 / 列表投影 | **按条数** | ~100 ns | `seq` + `rev` |
| 结果缓存 | 查询结果 / 游标快照 | 少量 | ~50 ns | 该 store 的 `seq` 变 |

**谁常驻内存**

| 数据 | 常驻？ | 理由 |
|---|---|---|
| 业务数据 | ✅ 行对象 + 位图索引 | 几万行 × 200 B ≈ 10 MB；位图每属性每万行 1.25 KB |
| mock | ✅ 全驻 | 几千条 |
| capture 会话索引 | ✅（每 session 一行） | 用于跳过不重叠的会话 |
| capture 列数据 | ❌ 靠 page cache | 按需只读需要的列 |
| agent 文档 | ❌ 只驻外壳 | 文档永不 parse |

**什么时候不该自己做缓存**：一次访问已经是「一回 pread + TypedArray（1.8 ms / 4 MB）」时，再加对象缓存收益很小，
却凭空引入一类失效 bug。**只有「需要解析 / 需要跨文件拼装 / 需要聚合」的结果才值得缓存。**
→ 抓包的原始列不缓存，抓包的**列表行投影**要缓存。这个区分省掉一半实现量。

**失效只有一条规则**：每个 store 一个单调 `seq`，任何写让 `seq++`；缓存项记录自己基于的 `seq`，
变了即失效。**不做 TTL（只做兜底清理），不做依赖图追踪。**

### 3.7 统一门面 API 与一致性模型

```ts
interface Db {
  store: { biz: Store<BizRow>; capture: Store<CapRow>;
           mock: Store<MockRow>; agent: Store<RunRow> };
  query<T>(spec: QuerySpec): Promise<{ rows: T[]; cursor: string | null }>;
  commit(batch: Op[]): Promise<{ seq: Record<Namespace, number> }>;
  subscribe(ns: Namespace, since: number, cb: (ev: ChangeEv) => void): () => void;
  flush(): Promise<void>;                        // 退出前强制提交
  stats(): { dirtyBytes: number; fsyncP50: number; cacheHit: number };
}
```

必须写清的一致性模型（不写清后面一定扯皮）：

- 单进程单写者 → 不需要分布式事务。
- **read-your-writes**：`commit` 返回后立即可读。
- **跨 store 无原子性**：`biz` 与 `capture` 不在一个事务里。真需要就合成一个 batch，靠同一条 commit record 保证「要么都可见、要么都不可见」。
- **订阅是至少一次**：可能重复投递，客户端按 `(ns, seq)` 去重。

### 3.8 实现顺序（按依赖排，不按重要性）

| 阶段 | 内容 | 行数 | 为什么这个顺序 |
|---|---|---:|---|
| P1 | IO 薄层：fd 池、定块读、TypedArray 视图、批量写 | ~200 | 所有 store 都要，且立刻能复现 §3.1 的数字 |
| P2 | Buffer Pool + Committer（group commit） | ~450 | 唯一能解决「fsync 20 ms」的地方 |
| P3 | 门面 + seq/订阅 + 对象缓存 | ~350 | 把四个 store 收进一套 API |
| P4 | capture 会话分段 + 清空 + 开关 | ~500 | 最大的数据量在这里 |
| P5 | biz CoW 页 + 位图 | ~1400 | 最重，但收益最确定 |
| P6 | mock 内存 + journal | ~250 | 最简单，可以最后 |
| | **合计** | **~3150** | |

**P1 + P2 可以立刻在现有 JSON 存储上生效**：把 `writeFileSync` 换成「进 buffer pool + group commit」，
不改数据结构就能把「10k 条 50 ms/次」压成「一个窗口 20 ms」。这是全项目最便宜的一次验证（§0.5）。

### 3.9 Node 单线程的现实约束

- 一个慢查询阻塞所有请求。凡可能 > 8 ms 的操作必须分片让出（每 200 行 `setImmediate`）。
- 实测 100 万行扫描 3.67 ms → **单次查询上限约 200 万行**。再大必须游标返回或分片。
- `worker_threads` **只能拿主线程给的内存副本**，绝不能自己读数据文件 —— 否则又变成多读者，
  §2 的收益（内存主存、单一失效链）全部归零。
- 后台清理（死段回收 / compact / 全量导出）应由 Swift 以低 IO 优先级 spawn 子进程：
  `setiopolicy_np(IOPOL_TYPE_DISK, IOPOL_SCOPE_PROCESS, IOPOL_THROTTLE)`。
  不做的后果很确定：清空 73 GB 后 App 卡几分钟（§5.5 证明删除要跑 5 分钟以上）。

### 3.10 不做什么（越界就真变成造数据库了）

| 不做 | 因为 |
|---|---|
| SQL 解析器 / 查询优化器 | 筛选器写死，执行计划编译期确定 |
| MVCC / 快照隔离 / 页级锁 | 单写者单进程，读写天然串行 |
| WAL + checkpoint 时序 | CoW + 双 meta 替代（§4.2） |
| doublewrite buffer | CoW 旧页从不被覆盖 |
| 通用 B-tree | 位图 + 有序数组 + 哈希已覆盖固定筛选器 |
| 分区 / 复制 / 分布式 | 单机 |
| 自研大规模向量索引 | 实测：建桶 10.4 s、recall@10 仅 0.60、只快 4 倍 → 超 20 万条外挂 |
| 自研大规模全文检索 | trigram 倒排只做名称/路径这种短字段；正文用即时 grep（解压 + 字节搜索 ≈ 1 GB/s） |

**边界判据**：一旦产品要「用户自定义任意字段组合查询 + 多维排序」，或出现「关联的关联」多跳，
立刻回到 SQLite —— 那一刻你在实现的就是 B-tree + 查询优化器（§8.3）。

## 4. 业务数据引擎（typed）：CoW 页 + 位图

### 4.1 为什么写死筛选器让磁盘层大幅简化

**B+tree 存在的唯一理由：索引在磁盘上要能增量修改。**

筛选器一旦在编译期固定，索引就可以全部搬进内存；磁盘只剩三件事要做：
**变长记录存储、页分配、崩溃一致性**。B+tree 的平衡、分裂、合并、页内重排全部消失。

这就是「自研够用」和「自研更快」的分界点 —— 不是妥协，是砍掉了不需要的部分。

### 4.2 磁盘层：CoW 页存储（LMDB 模型，无 WAL）

```
biz.pages     4 KB 页文件，只追加新页，永不原地覆盖旧页
meta.a/b      各带 CRC32，交替写入，保存 root_page + page_count + free_hint
```

写入流程：

```
1. 从 free_hint 分配新页
2. 把变更后的行/页写到新位置（旧页不覆盖）
3. 更新内存中的 root
4. 写 meta[1 - active] → fdatasync → 切换 active 标记
```

崩溃恢复：读两个 meta，取 **CRC 通过且 page_count 最大** 的那个。
**没有 WAL、没有 replay、没有 checkpoint 时序** —— 崩溃安全由「旧页从不被覆盖」这条物理约束保证。

- 空间放大：每次写产生若干垃圾页 → 启动时重建 free list + 后台 vacuum（垃圾水位 > 40% 触发）。
- 页内布局：`[u16 n_slots][u16 free_ptr][slot offset array][行数据从尾部向前生长]`。
- 行编码：定长字段内联；变长字段存 `(pool_off u32, len u16)`，字符串池按页分组。

### 4.3 内存层：三个索引，启动重建

| 索引 | 结构 | 用途 | 内存（10 万行） |
|---|---|---|---|
| 行指针表 | `id → (page, slot, ver)` 开放寻址哈希 | 主键点查 | ~4 MB |
| 位图索引 | 每「字段 × 取值」一个 `Uint32Array` | 枚举 / 低基数过滤 | 每维度 ~12.5 KB |
| 排序数组 | 有序 `Uint32Array` rowid | 时间 / 名称 / 评分排序视图 | 每视图 400 KB |

启动重建：扫 11 万页（约 45 MB），顺序读 + 建索引 ≈ **60–120 ms**。
超过 200 ms 就加「内存索引 snapshot」（二进制直读，免重建），别让它成为启动路径的瓶颈。

### 4.4 筛选字段的索引选型

| 字段类型 | 结构 | 单次成本（10 万行） |
|---|---|---:|
| 枚举 / 低基数（部门、状态、级别、类型） | **位图** | 位与 ≈ 3 µs |
| 时间范围 | 有序 `i64` 数组 + 二分 | 0.5 µs |
| 数字范围（评分、年龄） | 有序数组 / 分段位图 | 1–3 µs |
| 关联 id | 位图（中基数）或哈希桶 | 3 µs |
| 精确匹配高基数串（email、工号） | 开放寻址哈希 | 0.1 µs |
| 名称前缀 / 包含 | **trigram 倒排**（要单独加） | 10–50 µs |

**位图比 B-tree 快，不是「够用」而是「更快」**：B-tree 是逐条 seek（每条一次分支预测失败），
位图是一次遍历批处理 64 行。三条件交集：B-tree 100–500 µs vs 位图 3 µs。

**不要预计算「维度组合」位图**：运行时位与 3 µs 已经够，预计算随维度数指数爆炸，
还失去「新增筛选器不改磁盘格式」的灵活性。

### 4.5 查询执行：固定筛选器 → 固定执行计划

```ts
function query(f: { dept?: string[]; status?: string; levelGte?: number; since?: i64 }) {
  let bm = allRowsBitmap();
  if (f.dept)     bm = and(bm, union(deptBitmaps(f.dept)));
  if (f.status)   bm = and(bm, statusBitmap(f.status));
  if (f.levelGte) bm = and(bm, rangeBitmap(levelBitmap, f.levelGte));
  if (f.since)    bm = and(bm, timeRangeBitmap(f.since, Infinity));
  return sliceOrdered(bm, cursor, 50);   // 位图天然有序 → 分页零成本，无 OFFSET 退化
}
```

需要按某字段排序时：从对应的排序数组里按位图过滤（顺序扫数组 + 判定位），仍是无跳转的顺序访问。

### 4.6 四条必须守住的边界

1. **位图只适合低基数**（≤ 几十万个不同值）。`id` / `email` / 时间戳不能建位图。
2. **每次更新要同步改所有相关位图**：一个字段变更 = 旧值位图翻 0、新值位图翻 1，O(1)，但**别漏**。
3. **写死的筛选器里若含「名称包含」，现在就加 trigram 倒排**（+150 行）。事后加要改磁盘格式。
4. **不做 JOIN 执行器，但必须做引用索引**（§8）：外键用「分桶位图 + 批量解析」，聚合用声明式累加器。

### 4.7 最容易出 bug 的地方不是查询，是索引维护

位图/反向索引一旦漂移，**不抛异常，只返回错数据**。你会等到某天「研发部少了一个人」才发现，
而且已经无法回溯是什么时候错的。所以这个测试必须第一天就写：

```
随机 1000 次增删改后，对每个外键与每个位图维度：
  bitmap(x) / backref(x) 的结果 ≡ 全表扫描 {r | r.f = x} 的结果，逐条比对
```

它比崩溃测试更早能救你：崩溃是「看得见的失败」，漂移是「看不见的错误」。

### 4.8 实现量、崩溃测试与成本

| 模块 | 行数 |
|---|---:|
| 页存储 + CoW + meta 原子切换 + free list + vacuum | ~600 |
| 行编码（定长槽 + 变长溢出池） | ~200 |
| 位图索引 + 查询执行器（and/or/not/range） | ~250 |
| 排序数组 + 增量维护 | ~150 |
| 启动重建 + 索引 snapshot | ~150 |
| **合计** | **~1400 行 / 1.5–2 周**（含 3 天崩溃模拟） |

对比「自研通用 B-tree 引擎」的 5,000–15,000 行：砍掉的正是最不需要的部分（磁盘索引结构）。

必须测的三个崩溃场景：
1. 写新页到一半被杀 → meta 未切换 → 恢复用旧根，新页成为垃圾。
2. meta 写到一半被杀 → CRC 不过 → 用另一个 meta。
3. 连续 1000 次 `kill -9` + 重启 → 索引与页文件始终自洽。

## 5. 抓包引擎（log）：会话分段 + 列存

### 5.1 为什么不用 B-tree

| 维度 | B-tree | 列存分段（单文件内） |
|---|---|---|
| 写 | 每次 insert 改页、可能分裂，写放大 10–50× | 纯顺序 append，写完不管 |
| 查 | 低选择性过滤（时间范围 + status/host）要随机 seek | 顺序扫定长列，缓存友好（100 万行 status = 2 MB，1–2 ms） |
| 维护 | 删一年要逐行 delete + vacuum | 封档即不可变 → 零 compaction、零索引重建 |
| 淘汰 | O(行数) | **O(段数)：标记段组 dead** |

第 4 条在真实产品里权重最高：用户点「清空」或「只保留 30 天」，B-tree 那条路会把 App 卡死。

### 5.2 分段粒度是「录制会话」，不是「自然日」

抓包有开关，一天里 95% 的时间没在抓。按天分段时，查「今天 9:00–10:00」要把今天全部列区读一遍；
按会话分段时，先用会话表（常驻内存）的 `[started_at, ended_at)` 跳掉所有不重叠的会话，只读 1–3 组段。

而且「清空全部」和「删这次录制」的用户认知边界，恰好都是会话。

### 5.3 会话段与列区清单（精确到字节）

一个会话 = 一组段（`cap_meta` 段 + `cap_body` 段），在 `store.db` 里仍按列连续排布，
所以「按列只读」的收益完全保留：**只 pread 需要的 1–2 列所在的那一小段字节范围**。

```
会话 s-20261030T2112-a3f1        = 一组段的逻辑名（段头里带 session_id）
  chunk-000                      = 一个列区组，命中 64 MB 或 30 min 即切
    列区头                        {"rows":10234,"cols":{...},"dict":{...},"ver":1}
    ts       u64 × rows          8 B/行
    host     u32 × rows          4 B/行（字典编码 → host 字符串池）
    method   u8  × rows          1 B/行
    path     u32 × rows          4 B/行（字典编码）
    status   u16 × rows          2 B/行
    dur      u16 × rows          2 B/行（ms，上限 65 s，超出置顶）
    size     u32 × rows          4 B/行
    flags    u8  × rows          1 B/行（命中 mock / 压缩 / 截断）
    body.idx (u64 off, u32 len, u32 hash32) × rows   16 B/行
    body     小于 8 MB 的 body 连续追加区（`cap_body` 段）
    body-big 大于 8 MB 的 body 单独占段，按 hash 前两位分桶（段头标 big=1）
```

- 段头里的 `rows / len / crc32` 就是自描述信息，**列区头仍然是明文 JSON**（§16.5 的要求）。
- 段的物理偏移不连续也没关系（first-fit 复用死段），列区头里记录每列相对段头的 offset 即可。

**为什么 chunk 再切一层**：不是为了查询，是为了写入。正在追加的列文件涨到 2 GB 后，
重映射与 `ftruncate` 都会变慢，封口后也不好压缩。切到 64 MB 让「正在写的最后一块」永远很小。

### 5.4 查询路径（示例：status=500 + 近 3 天）

```
1. 选会话：按会话表的时间区间跳选，通常 1–3 组段
2. 只读需要的列：ts.col + status.col（3 天约 60 KB）
3. 顺序扫 → 候选行号（不碰 host/path/body）
4. 命中行才查 body.idx，按 off/len 读 body
5. 分页游标 = (session, chunk, row_index)，天然 keyset，无 OFFSET 退化
```

### 5.5 清空：段标记 + 尾部截断 + 打洞（本机实测）

单文件没法「删目录」，清空改成三步，仍然是 O(段数) 而不是 O(字节)：

| 操作 | 实测 |
|---|---:|
| 把一组段标记 dead（改 meta + 一次 fsync） | **1–3 ms**（与数据量无关） |
| `ftruncate` 掉尾部连续的死段 | O(1)，< 1 ms |
| `F_PUNCHHOLE` 打洞 800 MB（1 GB 文件） | **125 ms**，`du` 立即 1024 → 224 MB |
| 打洞 100 MB / 1000 MB | 2.8–16.9 / **32.2 ms**（≈30 µs/MB） |
| 洞内复用写入 | **0.54 ms** |

```
① 封口当前会话（clean_close，停收新数据）
② 把该会话所有段标记 dead → 写 meta 双份 → 一次 fsync      ← 1–3 ms
③ 若死段在文件尾部连续 → ftruncate 到第一个死段起点        ← O(1)，空间立刻归还
④ 否则 → 记入 pending_reclaim：后续写入优先复用这些段；
        需要立刻归还空间时走打洞或后台 compact（见下表）
⑤ 重置该 namespace 的 seq，push {push:"reset", ns:"capture", seq:0}
```

**Node 没有 `fcntl`，所以「中间死段怎么归还」有三条路，必须选一条：**

| 方案 | 额外二进制 | 空间何时归还 | 实现量 | 建议 |
|---|---|---|---:|---|
| **A. 只标记 + 优先复用** | 否 | 不归还，但被复用，文件不再增长 | +80 行 | ✅ **先做这个** |
| B. 20 KB C helper 调打洞 | 是（编译期产物，需签名） | 立刻 | +120 行 + 60 行 C | 可选增强 |
| C. 后台 compact（活段前移重写） | 否 | 整理完成后 | +200 行 | 磁盘紧张时用 |

方案 A 的实际效果：清空后**列表立刻为空、seq 重置、磁盘占用不变但会被新数据填满**。
这就是 SQLite `DELETE` 不 `VACUUM` 的行为，用户能理解，只要 UI 说清楚（§15.5）。

### 5.6 录制开关：状态机 + 两道闸门

```
idle ──start──▶ recording ──stop──▶ closing ──(2s grace / 在途清空)──▶ idle
```

**归属判定必须用「事件时间」，不能用「到达时间」。** 关闭瞬间插件手里通常还有在途 POST 和积压队列：

| 记录的事件时间 | 到达时开关已关 | 处理 |
|---|---|---|
| `< session.started_at` | — | 丢弃（开关打开前的流量） |
| `>= session.ended_at` | — | 丢弃（关闭后的流量） |
| 在区间内 | 是 | **收下**（它确实发生在录制区间内，只是上传晚了） |

用到达时间会犯两种错：关闭时漏掉在途的最后一批；或把关闭后的静默流量补进历史时间线。

**隐私硬规则：重启后绝不自动恢复录制。** 上次崩溃时是 recording，重启自动开 = 在用户不知情时开始记录流量。

### 5.7 body 四条硬规则

| 规则 | 做法 | 收益 |
|---|---|---|
| 存原始 bytes | 不 base64、不 parse、不格式化（格式化是展示层的事） | 省 33% 带宽 + 省一次 parse |
| zstd 压缩 | JSON/HTML 通常压 5–10 倍，解压 ≈1 GB/s | NVMe 上基本白送 |
| 内容寻址去重 | **仅限 capture 命名空间内**；静态资源/健康检查/轮询响应可省 30–60% | 省的是最贵的那部分 |
| content-type 分级 | 图片/视频/字体/音频**不存 body**，只存 metadata + size + hash | 一条规则砍掉六到八成存储 |

**不要跨到 mock 池去去重**（早期方案里的错误建议，已撤回）：mock 通常只有几百到几千条，
即使 100% 命中已有抓包，节省的绝对量相对抓包总量只有千分位；而代价是确定的 ——
一旦共用内容池，「清空」就必须保住仍被 mock 引用的 body，从「整段丢弃」退化成
「遍历百万级 blob 判断存活」。**清空成本取决于有没有跨源共享。**

想省空间有正确做法：`fs.cpSync(src, dst, {mode: COPYFILE_FICLONE})`，APFS 写时复制，
两个独立 inode 共享物理块，删任一方互不影响。但它只对单文件有效，所以只给 > 8 MB 的 body 用。

### 5.8 规模估算与保留策略（必须在上线前定）

| 假设 | 元数据 | body |
|---|---|---|
| 每天 1 万条 | 1.5 MB/天 | 200 MB/天 |
| 保留 30 天 | 45 MB（可全内存） | 6 GB |
| 保留 1 年 | 550 MB（必须按需加载段） | 73 GB |

**元数据其实一直装得下内存**（只要按会话加载，不全量常驻）；真正撑爆磁盘的只有 body。
所以保留策略（保留 N 天 / 上限 X GB / 超限淘汰最旧会话）比存储引擎重要得多 ——
没有这条，任何方案半年后都会崩，而且崩的时候救不回来。

### 5.9 Chrome 插件通道：POST 批量帧，不要 WebSocket

| | WebSocket 长连接 | **HTTP POST 批量帧** |
|---|---|---|
| MV3 service worker 30 s 空闲被回收 | 连接必断，要写重连 + 补偿 | 无影响，下次唤醒补传 |
| Node 侧依赖 | 需要 `ws`（破「零依赖」） | 内置 `http`，零依赖 |
| 重试语义 | 自己做序列号 + 重放 | 天然（换 `batch_id` 重发） |
| 方向 | 服务端推送 | **客户端推送** ✅ |

抓包是纯「客户端往上推」的场景，长连接没有收益，只有故障来源。

**通道设计**：一个 POST = 一个二进制批量帧，内含 N 条记录，各带自己的 body 原件。
不要 JSON 套 JSON，不要 base64（插件侧 CDP 拿到二进制 body 本来就是 base64，
在插件里就 `atob` 转回 `ArrayBuffer` 再拼帧，别把 base64 往下传）。

**背压与幂等**：插件侧 IndexedDB 做本地队列；sidecar 返回 `{accepted, watermark, retry_after_ms}`，
插件删掉已确认的；重试用同一个 `batch_id`，sidecar 侧记 `applied_batches` 去重 ——
插件被回收、网络抖动、sidecar 重启都不会产生重复数据。

## 6. mock 引擎：内存主存 + tombstone

mock 和抓包的访问模式相反（少、可变、要单条删），存法也该相反：

```
mock.json      snapshot：全量常驻内存（千条级）
mock.journal   追加式：{op:"upsert"|"delete", id, payload?, at}
```

- 删除 = 写一条 tombstone 到 journal，**不立即删 blob**，延迟 5 分钟并给 `undo_token`（误删可恢复）。
- 启动 = load snapshot + 重放 journal（含 tombstone 过滤）。
- 周期性 compaction：journal > 2 MB 或 5 分钟时重写 snapshot。
- **不 fsync**：mock 是用户手工创建的少量数据，丢几条靠重放补，不值得付 20 ms。

**最容易出的 bug**：删 mock 时漏改路由表 → 请求仍会命中已删 mock 返回旧 body。
删除必须是一个 commit 里的两步：删记录 + 摘路由。

## 7. agent 引擎（doc）：shell + body 二分

### 7.1 支点：一条 5 MB 的 run 里，只有 200 字节参与索引

```ts
type RunShell = {
  run_id: string; agent: string; status: u8;
  started_at: i64; duration_ms: u32; bytes: u32;
  capture_id?: string;            // 关联抓包（ref）
  doc_off: u64; doc_len: u32;     // 指向 store.db 内 run_doc 段的定位信息
};
type BodyRef =
  | { kind: 'inline'; bytes: Uint8Array }                       // < 8 KB
  | { kind: 'range'; off: number; len: number }                   // > 8 KB，store.db 内的区间
  | { kind: 'none' };                                            // 不存（如静态资源）
```

**谁 parse，谁付钱；付一次就够，付两次是设计错误。**
- sidecar 永不 parse body（只搬 bytes、只给 offset）。
- 需要结构化时由消费方 parse 一次，结果进对象缓存。
- 列表与过滤永远只碰 shell。

### 7.2 三档 schema

| 档位 | 用于 | 索引能力 | 写入校验 |
|---|---|---|---|
| `strict` | 业务数据 | 位图 / 有序数组 / 哈希，全量 | 全字段校验，拒写非法值 |
| `loose` | AI 产物的外壳 | 只有声明字段可索引 | 声明字段校验，其余忽略 |
| `opaque` | body 本体 | **零索引**，只能按 id 定位 | 不校验、不解析 |

**硬规则：`opaque` 字段永远不能出现在 `WHERE` 里。** 如果产品需要按 body 里某个字段过滤，
那它就不该是 body，应该提升到 shell（这是产品决策，不是技术决策）。

### 7.3 一条 run 的完整生命周期

```
① 用户点「运行」→ 建 run 记录
   shell = {run_id, agent, status:'running', started_at}；body 空（不预分配）
② LLM 流式输出 → 每 200 ms 追加一次
   append(run_id, chunkBytes)   ← 只追加到 body 文件尾，只更新 shell.bytes → seq++
③ 用户中途打开 → 读前 4 KB 预览
   readRange(bodyRef, 0, 4096)  ← 0.27 ms 级，不 parse 全文
④ run 结束 → 封口
   status='done'；body 转只读；run 级 fsync 一次；异步算 embedding
⑤ 用户搜「上次那个改动我们讨论过什么」
   先走 shell 结构化过滤（agent / 时间 / 状态，微秒级）缩小到几十条
   再对这几百条做语义召回（毫秒级）
```

**第 ⑤ 步的顺序是本方案与「向量数据库」思路最大的分歧：向量不是入口，是收尾。**
agent 场景 90% 以上的查询是结构化的，把向量当第一入口等于主动把 160 ms 塞进主路径。

### 7.4 上下文窗口切片：AI 数据真正的专属能力

最典型的读不是「取一条记录」，而是「给模型喂一个预算有限的窗口」：

```ts
context(runId, { tokenBudget: 8000, strategy: 'head+tail' })
```

实现必须是「按字节区间读 + 估算 token + 边界对齐」，**绝不能先 parse 再裁剪**
（那是先付 10 ms 再丢掉 90%）。

### 7.5 向量：只在收尾用（实测结论）

| 规模（768 维） | 暴力全扫单次 |
|---|---:|
| 1 万条 | **16 ms** ← 交互边界 |
| 5 万条 | 77 ms |
| 10 万条 | 164–204 ms |
| 10 万条 × 128 维 | 28 ms |

实现细节也测了：8 路循环展开把 204 ms 降到 174 ms；**int8 量化在 V8 里根本不加速**
（150 vs 164 ms，只省内存，因为 JS 里仍要转浮点乘）；自建 IVF 桶：10 万条建索引 **10.4 s**、
查询 52 ms、`recall@10` 只有 **0.60** —— 只快 4 倍，召回还不可控。

所以：**< 2 万条用暴力（16 ms，代码最简单）；2–20 万先降维；> 20 万别自己做，外挂 wasm/native。**
增量写入反而便宜：挂到已有质心约 196 µs/条。

## 8. 跨表索引：五种「跨表」，只有一种是 JOIN

「要做跨表」这个需求必须拆开，因为五件事的成本差 100 倍：

| # | 实际需求 | 实现方式 | 实测成本 |
|---|---|---|---:|
| 1 | 列表里显示部门名 | 批量 `resolve()` 一次取回 | **0.24 µs/条** |
| 2 | 这个部门下有哪些人 | 反向 posting list | 21.7 µs / 4000 条（全表扫 580 µs，27×） |
| 3 | 找研发部的人产生的 run | **外键分桶位图** 半连接 | 125 µs / 10 万行 |
| 4 | 同时带 tag A 和 B | 有序双指针求交 | 13.8 µs / 2000²（Set 51.9 µs，3.8×） |
| 5 | 每部门 run 数 / 失败率 | 声明式累加器 | O(1)/次变更（纳秒级） |

**只有第 5 类，以及「用户自定义深度的多跳连接」需要真正的连接执行器。**
前四类只是索引 + 批量取 + 位运算的组合，一行 JOIN 都不用写。

一句话：**跨表索引 ≠ JOIN 执行器。前者你必须有，后者你几乎永远不需要。**

### 8.1 半连接：位图赢，而且不用额外结构

| 方式（10 万行目标表） | 500 个 id | 5 万个 id |
|---|---:|---:|
| `Set.has` 逐行判 | 2,450 µs | — |
| **位图逐行判** | **125 µs** | **182 µs** |
| 有序归并 | 153 µs | 662 µs |

位图的成本只取决于**目标表行数**，与 id 集合大小无关；而且它本来就是业务数据的索引结构，
不需要为半连接写第二套代码。（我原先以为「有序归并」最快，实测位图更稳。）

**更关键的一步：不要「先取 id 集合再构造位图」。**
低基数外键（部门、状态、类型）应该直接维护「按对端 rid 分桶的位图」：

```
dept 表 50 行 × 10 万行 → 625 KB，全驻内存
查「研发部的 run」= dept 表拿到 rid → 直接取该 rid 的位图 → 与其他条件位与
```

这就是谓词下推：**外键是编译期可展开的引用，不是运行期连接。**

### 8.2 引用要作为第一等对象，并显式声明

```ts
dept: ref('dept', { onDelete: 'restrict' }),      // 正向解析 + 反向索引 + 删除保护
tags: many('tag'),                                // 多对多边表
src:  ref('capture', { onDelete: 'dangling' }),   // 跨生命周期
```

`onDelete` 三策略**必须显式声明、没有默认值**：

| 策略 | 语义 | 用在哪 |
|---|---|---|
| `restrict` | 还有引用时禁止删对端 | 部门 / 组织这类主数据 |
| `cascade` | 删对端时连带删引用方 | 严格拥有的子记录 |
| `dangling` | 允许悬空，读时返回 null | **跨 namespace 一律用这个** |

`dangling` 是本地 App 的关键：既然抓包可整体清空，`mock.src_capture_id` 就必须是 `dangling`。
设成 `restrict` → 用户点清空会被 400 条 mock 挡住，功能不可用；
设成 `cascade` → 用户清空抓包，他的 mock 一起没了，数据事故。

### 8.3 边界判据（三条，任一成立就换 SQLite）

1. **多跳依赖**：A→B→C→D 任意深度，且路径由用户或数据决定
2. **动态聚合维度**：用户自选 `group by` 字段
3. **任意嵌套的 OR / NOT**：位图擅长 AND 与简单 OR，深嵌套会退化

第 1 条最容易越界 —— 一旦出现「关联的关联的关联」，你就在写查询优化器，那不是 500 行能收住的事。

### 8.4 两条硬规则（比查询更易出错）

- **引用更新必须与主记录写入在同一条 commit record 内**，否则崩溃后会出现「行在、索引不在」。
- **删除时先删索引项，再删主记录**；反过来会留孤儿索引。

## 9. 通信协议：改形状，不换传输

### 9.1 传输不是瓶颈，别在这里花时间

| 方式 | 单次 RTT | 评价 |
|---|---|---|
| loopback HTTP/1.1 keep-alive | 0.2–0.6 ms | 可 curl 调试，生态成熟 |
| Unix domain socket + 长度前缀帧 | 0.05–0.15 ms | 快、无端口、文件权限即鉴权；要自己写编解码 |
| stdio pipe（NDJSON） | ~0.05 ms | 生命周期天然绑定；单向流需多路复用 |
| NSXPCConnection | 低 | Node 侧无原生支持，要 native addon → 破「零依赖」 |

**结论：如果现在是 loopback HTTP，就留着。** 真要压 p99 再换 UDS。
真正的改动是协议形状：从「返回整份数据」改成「返回结果 + 分页游标 + 变更信号」。

### 9.2 四个信封

**① 命令（写）**
```json
{"v":1,"id":"req_01J...","op_id":"uuid","method":"doc.patch",
 "params":{"id":"note_42","expect_rev":8,"patch":{"title":"..."}},"deadline_ms":3000}
```

**② 响应（只回结果，不回数据）**
```json
{"v":1,"id":"req_01J...","ok":true,"result":{"seq":124,"rev":9},"elapsed_ms":1.4}
```

**③ 查询（强制分页 + 字段裁剪）**
```json
{"v":1,"id":"req_01K...","ok":true,
 "result":{"items":[...],"next":"eyJzIjoxLCJjIjowLCJyIjoxNzMyfQ","total_approx":12043}}
```
`next == null` 表示到底；`total_approx` 来自物化计数，别做精确 `count(*)`。

**④ 订阅（变更推送）**
```json
{"v":1,"push":"change","ns":"capture","seq":124,
 "ops":[{"e":"capture","id":"c_8f21","op":"u","rev":9}]}
```

- 只推 `(ns, entity, id, op, rev)`，**不推内容**。客户端按 id 本地重查（内存 3 µs / 文件 1 ms）。
- 服务端 16 ms 合并一帧（同一 id 多次变更只留最后一次），前端一次渲染。
- 积压超阈值 → 推 `{"push":"reset","ns":"capture","seq":0}`，客户端丢缓存重拉首屏。

### 9.3 幂等、乐观锁、背压、重连

| 问题 | 处理 |
|---|---|
| 重试导致重复写 | `op_id` + 服务端 `applied_ops` 去重（保留 24 h），重复请求直接返回原 `seq` |
| 并发编辑冲突 | `expect_rev` 不匹配 → `{ok:false,error:{code:"CONFLICT",details:{current_rev:9}}}` |
| 订阅推太快 | `max_inflight = 8 帧 / 1 MB`，超限降级为 `reset` |
| 断线重连 | `hello {since: last_seq}` → 从 journal 回放；`since < min(seq)` → `reset` |
| 慢请求堆积 | 每请求 `deadline_ms`，超时服务端取消并回 `{ok:false,error:{code:"TIMEOUT"}}` |
| sidecar 崩溃 | 客户端指数退避（100 ms → 3.2 s）+ 重启子进程 + `since` 补齐 |
| 写拼批 | 16 ms 内的编辑合成一个 `batch`，一次 `BEGIN…COMMIT`（实测 100 条 0.59 ms） |

**禁止长事务**：单事务不要超过 100 ms，否则脏页/journal 无法回收，文件会无限增长。

### 9.4 大 body 的 offset 交接（D6 的落地形式）

```json
{"method":"run.body","params":{"id":"run_8f21"}}
→ {"result":{"file":"store.db","off":7340032,"len":5243000}}
```

sidecar 只回定位信息，Swift 自己 `FileHandle` / mmap 读。三条硬约束：
**body 不进 Buffer Pool、不缓存、不过 IPC**。违反任一条，5 MB 大对象就会把热数据挤出 page cache——
这正是「把大 JSON 塞进数据库」会塌掉的根本原因。

### 9.5 协议演进

每个信封带 `v`，未知字段忽略；磁盘格式带 `ver`（见 §14 的空白项）。
新增字段永远可选，删除字段要先保留一个版本周期的双写。

## 10. 运行时与版本：把变量变成常量

### 10.1 先分清两个「Node 版本」

| | 谁决定 | 现状 |
|---|---|---|
| ① sidecar 跑在哪个 Node 上 | **你的打包** | 若 spawn 系统 node → 不可控 |
| ② 引擎用到哪个 Node API | 你的代码 | 纯 JSON 只用 2015 年的 API |

现在「纯 JSON + 随便哪个 node 都能跑」的优点是**它把可用性押在「能找到能跑的 node」上，
而这在 macOS 上本身是坏的**。

### 10.2 依赖用户的 Node 不是「版本风险」，是「必然失败」

六条独立原因同时成立：

1. **GUI 应用的 PATH 不含 shell PATH**：从 Finder 启动的 App，`PATH` 只有 `/usr/bin:/bin:/usr/sbin:/sbin`。
   终端里 `which node` 通，用户双击 App 时 `spawn('node')` 直接 ENOENT。
2. **nvm / fnm / volta 装的是 shell shim**，依赖 `.zshrc` 初始化，GUI 进程没有这段。
3. **Homebrew 双路径**：Apple Silicon 在 `/opt/homebrew/bin`，Intel 在 `/usr/local/bin`。
4. **可能根本没装**：你的用户是设计师、产品、测试。
5. **版本漂移跨度极大**：18 / 20（已 EOL）/ 22 / 24 / 26 同时在用。
6. **公证与沙盒**：Hardened Runtime 下 spawn bundle 外部的可执行文件会被签名校验拦住；沙盒直接禁止。

所以问题不是「兼容 18 到 26」，而是**「不要有第二个运行时来源」**。

### 10.3 自带运行时的代价（本机实测）

| 项 | 实测 | 含义 |
|---|---:|---|
| `node` 二进制 | **110 MB** | 未压缩 |
| gzip 后 | **36.4 MB** | 安装包实际增量 |
| `strip -x` 后 | **89 MB** | 省 21 MB，**strip 后仍可运行（已验证）** |
| 冷启动 | 0.09 s | 用户感知不到 |
| 进程启动到脚本首行 | 10 ms | 含 V8 初始化 |
| 空转 RSS | 33 MB | sidecar 固定成本 |
| 加载引擎 + 建 13 个列区 | +5.6 MB / 3.9 ms | 引擎自身几乎不占内存 |

**一次性多 36 MB，换来「版本」这个变量彻底消失。**

### 10.4 四种打包方式，选第一种

| 方式 | 产物 | 体积 | 升级脚本 | 评价 |
|---|---|---:|---|---|
| **A. bundle node + `.mjs` 源码** | `Resources/runtime/node` + `sidecar/*.mjs` | 110 MB（gz 36） | 改文件即可 | ✅ **推荐** |
| B. SEA 单可执行 | 一个 Mach-O | 110 MB+ | 要重编译 | 只在想藏源码时用，而 JS 源码本来也藏不住 |
| C. Bun `--compile` | 一个 Mach-O | 60–95 MB | 要重编译 | ❌ **换运行时**，`fs`/`Buffer` 语义有差异，上文全部性能数字作废 |
| D. 系统 JavaScriptCore | 0 字节 | 0 | — | ❌ 实测 `jsc` 只有整文件 `readFile/writeFile` 字符串接口，**无 position 读、无 fsync**，列存落不了地 |

A 的额外好处：hotfix 只需替换 `.mjs` 文件（配合重签），不必发新版 App。

### 10.5 签名与公证：三个会让 node 直接起不来的坑

实测官方 node 二进制：`flags=0x10000(runtime)`（Hardened Runtime 已开），entitlements 含
`allow-jit`、`allow-unsigned-executable-memory`、`disable-executable-page-protection`、
`disable-library-validation`、**`get-task-allow`**。

1. **重签必须带 JIT 相关 entitlement**。V8 需要把内存页改成可执行；缺
   `allow-jit` + `allow-unsigned-executable-memory`，node 启动瞬间被内核杀掉（`Killed: 9`），
   **没有任何日志**，表现就是「App 打不开」。
2. **`get-task-allow` 必须去掉**（官方二进制里是 `true`，方便调试），否则公证被拒。
3. **签名顺序必须由内向外**：

```
1. strip -x runtime/node                       # 会破坏原签名（实测 warning 确认）
2. codesign -f --options runtime \
     --entitlements node-ent.entitlements --timestamp runtime/node
3. codesign -f --options runtime … YourApp.app
4. xcrun notarytool submit … && xcrun stapler staple YourApp.app
```

最小 entitlements：

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0"><dict>
  <key>com.apple.security.cs.allow-jit</key><true/>
  <key>com.apple.security.cs.allow-unsigned-executable-memory</key><true/>
  <key>com.apple.security.cs.disable-library-validation</key><true/>
</dict></plist>
```

> **Mac App Store 渠道要单独验证**：沙盒 + JIT 是敏感组合，bundle 一个通用 JS 运行时
> 可能被审核判为「下载可执行代码」。Developer ID 直分发没有这个问题。

### 10.6 钉哪个版本：24 LTS

| 版本 | 状态（2026-10-30） | 建议 |
|---|---|---|
| 22 Jod | Maintenance，安全支持到 2027-04-30 | 可用，但快到期 |
| **24 Krypton** | 2026-10-20 转 Maintenance，支持到 2028-04 | ✅ **现在钉这个**：成熟、无新特性扰动 |
| 26 | 2026-10-28 刚转 Active LTS（两天） | 等 2–3 个 patch；V8 从 12.4 跳到 14.6，性能要重测 |
| 27 | Alpha | ❌ |

理由不是「新」，而是**不动**：Maintenance 阶段只有安全与严重修复，两次发版之间运行时行为不会悄悄变。

### 10.7 但启动检查要用「能力」，不用「版本号」

版本号是间接指标，而且会被 flag 增删骗到（26 删掉了 `--experimental-transform-types`，
带它启动会直接报错退出）。所以启动时跑能力自检（完整源码见附录 B）：

| 档位 | 内容 | 缺失时 |
|---|---|---|
| **FLOOR（10 项）** | `fs.*Sync` 全家族、`fsyncSync`、`renameSync`、**带 position 的 `readSync` 真读写验证**、Buffer 定长整数、TypedArray 视图、BigInt、`hrtime.bigint`、`Buffer.from(ab, off, len)` | **拒绝启动**，exit 78（EX_CONFIG） |
| NICE（6 项） | `rmSync`、`worker_threads`、`cpSync+FICLONE`、`zlib.zstd*`、`Array.at`、`structuredClone` | 走降级实现 |
| INFO | node / v8 / arch / icu / sqlite | 只记录，便于报障定位 |

最关键的是**带 position 的 `readSync` 是否真的生效**：它会真读真写一个临时文件验证偏移。
某些裁剪过的运行时会接受 position 参数但忽略它 —— 静态检查看不出来，而列存 100% 依赖这个语义。
这种错误的症状是「某天的数据和前一天一模一样」，是最难查的一类 bug。

### 10.8 自研引擎在版本上是净收益

| 依赖 | 版本地板 | 风险 |
|---|---|---|
| `node:sqlite` | **22.13+**（22.13 前要 flag；实测 22.22.2 已免） | 仍是 Stability 1.2（RC），26.x 内改过 API |
| 自研引擎 | **16+**（14 也行） | 只依赖 `fs` + `Buffer`，这套 API 从 0.12 到 26 语义没变过 |

**`node:sqlite` 是一条会被 Node 大版本推进而移动的地板；自研是一条钉死在地上的地板。**
所以「不想依赖 SQLite」和「担心 Node 版本」这两个诉求指向同一个答案。

## 11. 迁移与里程碑

### 11.1 从现有 JSON 迁移的四段（每段可回滚）

| 阶段 | 内容 | 验收 |
|---|---|---|
| **P0 埋点**（半天） | 在关键路径加计时：`read / parse / stringify / write / fsync / ipc`，写本地日志（p50/p99） | **先确认痛在哪一段**，别凭感觉换架构 |
| **P1 止血**（1–2 天，不动存储） | 写合并（200 ms debounce + 失焦/退出强制 flush）；原子写 `tmp → fsync → rename`；追加 journal + 启动重放 | 10k 条从 50 ms/次 变为每 200 ms 一次 |
| **P2 双写影子期**（3–5 天） | JSON 仍是真源，每次写同时写新存储（失败只记日志）；随机 200 条逐字段对拍，连续 3 天零 diff | 对拍零差异 → 才允许切读 |
| **P3 切读再切写** | 先让 Swift 读新存储，观察 1 周；再关掉 JSON 写 | JSON 降级为「导出格式」 |

`P1` 的四步只用 `openSync / writeSync / fsyncSync / renameSync` —— **2015 年的 API，任何 node 都能跑**。
做完它就能回答「性能到底还差多少」，而不必先赌一个架构。

### 11.2 三个里程碑

| 里程碑 | 内容 | 行数 | 验收标准 |
|---|---|---:|---|
| **M1 能跑** | IO 薄层 + Buffer Pool + Committer + agent doc 引擎 | ~900 | 5 MB run 流式追加 100 次不卡；现有 JSON 存储的 10k 条写入 50 ms → 20 ms |
| **M2 能用** | biz + capture 引擎 + 门面/订阅 | ~2200 | 10 万行三条件过滤 < 200 µs；抓包百万行范围查询 < 12 ms |
| **M3 好用** | 对象缓存 + 上下文切片 + 向量旁路 | ~800 | 上下文切片 < 3 ms；向量有降级路径 |

1. 抓包 body 全量存 or 按需存（§14）
2. 业务数据真实规模与筛选器数量（§14）
3. 是否存在多跳关联（§8.3）

## 12. 反模式清单（踩了等于白做）

| 反模式 | 后果 |
|---|---|
| 列表接口返回全表 / `SELECT *` 式返回 | 一次 2.5 MB 序列化 ≈ 16 ms，IPC 变成瓶颈 |
| 逐条 `fsync` | 上限 50 次/秒，直接不可用（§3.1） |
| 用 TTL 做主要失效手段 | 「改了不刷新」的经典 bug；TTL 只能做兜底清理 |
| 把大 body 与热数据混在同一段 | 段是回收与缓存的最小单位，混放会让清空与 buffer 管理都退化成逐字节 |
| 让 Swift 也实现一套磁盘格式解析 | 两套 fuzz、格式升级双端同步，代价翻倍 |
| `OFFSET` 深分页 | 越翻越慢，必须用 keyset / 位图游标 |
| 预计算维度组合位图 | 随维度数指数爆炸，且失去「加筛选器不改格式」的自由 |
| 跨 namespace 共用 body 段 | 清空无法整段丢弃，退化为逐 blob 判断存活（§5.7） |
| 用到达时间判定录制归属 | 漏掉在途批次，或把关闭后的流量补进历史（§5.6） |
| 清空时同步 compact / 重写全库 | 73 GB 重写要几十秒到几分钟，期间所有 IPC 超时，sidecar 假死（§15.4） |
| 用版本号判定运行时 | 被 flag 增删骗过，必须按能力自检（§10.7） |
| 让 `worker_threads` 自己读数据文件 | 又变成多读者，内存主存的收益全部归零（§3.9） |
| 只索引不校验索引一致性 | 索引漂移不抛异常，只返回错数据（§4.7） |

## 15. 最终形态：一个文件（已采纳）

> 上一版给的是「目录树」，本节按你的决定改成**单文件**。改完之后读性能不变、备份更好，
> 代价集中在「空间回收从瞬时变成最终一致」和「可读性红利消失」两点 —— 两条都会在下文交代。

### 15.1 结论

**落盘就是一个文件：`store.db`。** 用户视角是一个可拖拽、可拷贝、可备份的文件；
内部是「区段表 + 段序列」，不是目录树。

| 你关心的 | 单文件后 |
|---|---|
| 读性能 | **无损**（`pread` 只认 offset，与文件边界无关；fd 从数百降到 1，反而略快） |
| 写性能 | **无损**（写入位置由区段表决定，与目录/文件无关） |
| 备份 | **更好**（实测 clone 1 GB ≈ 0 ms） |
| 清空 | 仍 O(段数)，但空间回收变成最终一致（§15.5） |
| 可读性 | **变差**（`cat run.json` 不再可能），只能靠 §16 的 `store` 命令 |

### 15.2 内部结构

```
store.db
├── [0, 4K)      文件头      magic "NSTORE" + u16 format_ver + u16 seg_size + 保留
├── [4K, 8K)     meta.a      区段表 + 各家族 seq 水位 + pending_reclaim，CRC32
├── [8K, 12K)    meta.b      同上，交替写入；恢复时取 CRC 通过且 gen 更大的那个
└── [12K, EOF)   段序列      每段 16 MB，头部 64 B
                              {magic, ver, type, rows, len, crc32, session_id, flags}
```

- `type ∈ {biz_page, cap_meta, cap_body, run_doc, free}`。
- **区段表**：`[{type, off, len, live, session_id}]`，与目录树等价，只是记录在 meta 里而不是文件系统里。
- **分配**：first-fit 找 `live=false / type=free` 的段；不足则 append 到 EOF。
- **段内仍是定长列**（§5.3），列区头是明文 JSON，任何语言可解析（§16.5）。

### 15.3 为什么读性能不受影响

三个原因，都不是「差不多」而是「严格不变」：

1. `pread(fd, buf, len, offset)` 走的是同一套页缓存，**多文件与单文件的差别只是 offset 空间是否连续**。
   实测「扫 8 MB 列 1.81 ms」这个数字与文件个数无关。
2. 唯一真实变化是 **fd 数量**：旧方案每个 chunk 要开 11–13 个文件，实测 `open+close × 13 = 306 µs`；
   单文件只要 1 个 fd → **这笔开销直接消失，读数略快**。
3. TypedArray 零拷贝视图、`F_NOCACHE` 旁路、大 body 不入 buffer pool —— 三条优化全部保留。

### 15.4 清空的三个实现档位（决定你要付多少）

| 档位 | 机制 | 空间归还 | 实现量 | 适用 |
|---|---|---|---:|---|
| **A** | 段标记 dead + 尾部 `ftruncate` + 死段优先复用 | 尾部立即，中间不归还但复用 | +80 行 | ✅ 起步 |
| **B** | A + 20 KB C helper 调 `F_PUNCHHOLE` | **立刻**（实测 800 MB/125 ms） | +180 行 | 用户抱怨占用时 |
| **C** | A + 后台 compact（活段前移重写） | 整理完成后 | +200 行 | 磁盘紧张或要"用完就干净" |

三档共用同一份区段表，所以 A → B → C 是**增量升级，不需要改磁盘格式**。
推荐：先 A，上线后看用户是否真的在意「清空后占用不降」；在意就加 B。

### 15.5 空间语义变了，UI 必须跟着改

| | 旧（目录树） | 新（单文件） |
|---|---|---|
| 点「清空」后列表 | 立刻空 | 立刻空（一样） |
| 点「清空」后磁盘 | 立刻少 73 GB | **可能不变**（等复用或整理） |

所以 UI 必须给两个信息：占用条 + 「可回收 X GB」按钮（触发档位 B/C）。
**不说清楚，用户会认为「清空没生效」** —— 这是单文件方案最容易踩的产品坑。

### 15.6 附加收益：备份与迁移

```
备份：await db.flush() → cp -c store.db backups/20261030T2300.db     # clone，近似 0 秒
迁移：flush + 停写 → 拷贝/打包这 1 个文件
恢复：rename store.db → store.db.bad，再 rename backups/<ts>.db → store.db，重启（O(1)）
多实例：NODESTORE_PATH 指向不同的 .db 文件
```

实测：`cp -c` 克隆 1 GB 单文件 **≈0 ms**（APFS clonefile，零拷贝）；而旧方案 1.3 万个文件要 4.3 秒。
**这是你选单文件换来的最大实惠。** 因此也不再需要 macOS package 那套技巧。

### 15.7 单文件的代价（必须写清，别只报喜）

| 代价 | 缓解 |
|---|---|
| 空间回收最终一致 | UI 显示「可回收」+ 档位 B/C（§15.4、§15.5） |
| 单点损坏：文件头或区段表坏了影响全库 | 双 meta + CRC + 每段自描述头 + 定期 clone 快照；恢复时逐段校验、丢弃坏段 |
| 局部淘汰不能靠「删文件」 | 打洞或 compact（§15.4） |
| **可读性红利消失**：`cat run.json` 不再可能 | 必须落地 §16 的 `store cat / dump / export` —— 这条最容易被忽略 |
| 大文件系统的稀疏文件信任问题 | 只用 `ftruncate` 与（可选）打洞，不依赖预分配稀疏；`du` 与逻辑大小分开报 |

### 15.8 与 SQLite 的最终对照

| | SQLite | 本方案（单文件） |
|---|---|---|
| 物理形态 | 一个文件 | **一个文件** |
| 内部结构 | B-tree + 页 | 区段表 + 段 + CoW 页 |
| 清空 | `DELETE` + `VACUUM`（O(n)） | 段标记 + 截断/打洞（O(段数)） |
| 备份 | 拷贝 | clone（≈0 ms） |
| 可读性 | 靠 `.dump` | 靠 `store dump`（§16） |

一句话：**形态一样是「一个文件」，但内部不是 B-tree，而是「区段 + 每类数据自己的结构」。**

### 15.9 对格式版本的要求

`format_ver` 出现在两处，**必须同时校验、同时升级**：文件头（全局）+ 每段头（单段）。
区段表里还要留 `min_reader_ver`，让新版本能在「读旧库」时判断是否需要就地升级。

## 16. 可读性、可诊断性与数据可携带性

> 直接回答：**分四档，一半可读一半不可读。** 而且「不可读」不是缺陷，是必须用工具补回的债。

### 16.1 逐项盘点：哪些能直接用眼睛看

| 数据 | 实际格式 | 可读性 | 怎么看 |
|---|---|---|---|
| `run_doc` 段（agent 本体） | **原样 JSON** | ★★★★★（内容）/ ☆（不是独立文件了） | `store cat run_8f21 > x.json`，内容逐字节等于原始输出 |
| `mock` 段 + journal | JSON / NDJSON | ★★★★☆ | `store dump mock` |
| 会话表、列区头 | 明文 JSON（段内） | ★★★★☆ | `store dump capture --sessions` |
| 文件头 + 段头 | 定长二进制（magic/ver/rows/crc） | ★★★☆☆ | `store info`，或直接 `xxd store.db \| head` |
| `cap_body` 段 | zstd 压缩的**原始 bytes** | ★★★★☆（内容） | `store cat` 解压后与浏览器看到的一模一样 |
| `cap_meta` 段里的列区 | 定长二进制（8/4/2/1 字节列） | ★☆☆☆☆ | `store dump capture` 转 NDJSON |
| `biz_page` 段（+ meta.a/b） | 4 KB 页 + 槽位目录 + 变长池 | ☆☆☆☆☆ | **必须**工具，肉眼无解 |

一句话：**不可变的大对象天然可读；可变的小数据不可读。**

原因不是随手选的：
- body 之所以可读，是因为它「永不 parse、不改写、不 base64」—— 存进去的是原始字节，读出来还是原始字节。
- 业务数据之所以不可读，是因为它被拆成了「页 + 槽位 + 变长池 + 位图」，为了 O(1) 更新和位图过滤。

### 16.2 一个反直觉的事实：SQLite 也不可读

`sqlite3 db` 用 `cat` 看同样是乱码。人们觉得它「可读」，是因为有：

| SQLite 的工具 | 作用 | 等价物我们有没有 |
|---|---|---|
| `sqlite3 db ".schema"` | 打印表结构 | ❌ 要自己做 |
| `sqlite3 db ".dump"` | 全库导出为 SQL 文本 | ❌ 要自己做 |
| `sqlite3 db "select …"` | 任意查询 | 半（固定筛选器） |
| DB Browser / DataGrip | 图形化浏览 | ❌ 要自己做（或等 Swift UI） |

**结论：可读性 ≈ 工具链成熟度，不是格式属性。**
自研而不提供工具，可读性就是 0；提供了，可读性可以**超过** SQLite ——
因为我们的 body 是原文件，SQLite 里存的大 JSON 反而要先 `SELECT` 再 `parse`。

### 16.3 一个设计红利：性能最优的选择恰好也是可读性最好的

对比两种存 body 的方案：

| 方案 | 性能 | 可读性 |
|---|---|---|
| 归一化后存进表结构（JSON → 字段 → 页） | 每次读要反序列化 + 拼装，300 KB ≈ 1.7 ms 起 | 不可读，还要靠工具还原 |
| **原样字节落文件（本方案）** | 读盘 0.27 ms，offset 交接后 0 解析 | **`cat` 就能看** |

这是少见的两头都赢。但**业务数据没有这种红利**：要做 O(1) 更新 + 位图过滤，就必须编码成页格式。
所以可读性在这个家族上必须**显式买**（工具），而不是指望格式。

### 16.4 四项工具义务（不做，这套设计就是黑盒）

随 sidecar 一起发布一个 `store` CLI（约 300 行，复用引擎读路径）：

**① `store dump` —— 二进制表 → NDJSON**
```
$ store dump biz.user --limit 2
{"id":"u_1024","name":"张远","dept":"R&D","level":7,"status":"active","_rev":3}
{"id":"u_1025","name":"李岑","dept":"Design","level":5,"status":"leave","_rev":1}
```
支持 `--where dept=R&D`（复用位图执行器）、`--limit`、`--since-seq`。

**② `store cat` —— body 原样输出**
```
$ store cat capture c_8f21            # 解压后写 stdout，可直接 | jq
$ store cat run_8f21 --off 0 --len 4096   # 只取头部，不 parse
```

**③ `store check` —— 一次性自检报告（用户可自己跑，把输出发给你）**
```
$ store check
biz      meta.a CRC ok · meta.b CRC ok · active=a · 102,431 rows · 索引对拍 8/8 一致
capture  37 sessions · 1,204 chunks · 末 chunk 未封口(正常) · 孤儿 blob 0
runs     512 个 · 缺 shell 0 · body 缺失 0
mock     1,024 条 · journal 12 条待 compaction
总占用   6.4 GB  (biz 45 MB / capture 5.9 GB / runs 480 MB / mock 1 MB)
```
这一条的价值不在于技术，在于**售后**：没有它，用户报「数据没了」你只能猜。

**④ `store export` —— 全量导出（数据可携带性）**
```
$ store export --out ~/Desktop/export/ --format ndjson
```
100% 可还原：导出后再 `import` 回来，逐字段一致。这是用户「我的数据能不能拿走」的唯一答案，
也是产品在隐私声明里能写的那句话的依据。

### 16.5 格式自描述的三条最低要求

1. **每个二进制文件头 8 字节**：`NSTORE\x01\x00` + `u16 format_ver`。没有 magic 的文件一律视为损坏，不要猜。
2. **每个列区头必须是明文 JSON**：列名、类型、字节宽度、行数、字典表；全局结构由 `store info` 输出等价信息。任何语言都能据此写解析器。
3. **schema 跟着文件走，不只存在代码里**。否则三年后没人知道第 7 列是 `status` 还是 `flags`。

判据一句话：**一个没有源码的人，能否只凭目录里的 JSON 写出解析器？** 不能，就是不合格。

### 16.6 如果「可读优先」，要付多少钱

| 方案 | 实现量 | 体积 | 点查 | 清空 | 可读性 |
|---|---:|---:|---:|---|---|
| 页文件 + 工具（本方案） | 1400 + 300 行 | 1× | 3 µs（内存） | 1.59 ms | 工具后 ★★★★☆ |
| NDJSON + offset 索引 | 600–900 行 | **2–3×** | 5–20 µs | **O(n) 重写** | ★★★★★ |
| SQLite | 0 行 | 1× | 7 µs | O(n) | 工具后 ★★★★☆ |

NDJSON 路线的问题不在读，在两个地方：**体积翻倍**（JSON 的键名重复、数字变字符串），
以及**清空必须重写文件**（§15.3 那条 O(n)）。

**判据：可读性不能当第一优先级，但必须当验收项。** 把它当第一优先级，你会为了 `cat` 方便
放弃 O(1) 清空和 3 倍空间；把它当不存在，你会在第一次数据事故时彻底失明。

### 16.7 一条硬规则：可读性预算

> **任何不可读的落盘文件，必须同时满足：**
> ① 能在 ≤3 条命令内导出为文本；
> ② `store export` 能 100% 还原为 NDJSON；
> ③ 用户不依赖你远程协助，自己跑 `store check` 就能产出一份可诊断的报告。

这三条写进 §13 的验收表，和性能指标同级。做不到就不算「完成」。

### 16.8 一个便宜的可读性折中：journal 用 NDJSON

- **commit record 与 mock journal 用 NDJSON**：追加日志本来就不需要紧凑（占总体积 < 1%），
  可读性几乎免费，还能 `tail -f` 实时看「刚才写了什么」。
- **页区与列区仍二进制**：那是热路径，不妥协。
- 效果：**最近 N 条变更是可读的**，历史是二进制但可 dump。这个组合覆盖了 90% 的排查场景。

### 16.9 附带收益：可读性直接决定「能不能自查」

| 场景 | 没有工具 | 有工具 |
|---|---|---|
| 用户说「抓包丢了几条」 | 你只能猜是背压、开关还是崩溃 | `store check` + `tail journal` 定位到具体 session |
| 用户说「导出的数据少了」 | 无法验证 | `store export` 对拍行数 |
| 你自己改格式 | 靠记忆维护两套解析 | `meta.json` 是唯一真相 |
| 三年后接手的人 | 读代码猜 | 读 `meta.json` 就懂 |

## 附录 B　`runtime/probe.mjs` 源码（可直接用）

> 用途：sidecar 启动第一毫秒自检运行时能力。`--json` 给 Swift 解析，`--strict` 缺必需能力则 exit 78（EX_CONFIG）。
> 用法：`node runtime/probe.mjs --json --strict`

```js
/**
 * 运行时自检（capability probe）
 *
 * 目的：在 sidecar 启动的第一毫秒，用「能力」而不是「版本号」判定运行时是否可用。
 * 版本号是间接指标（22.13 与 22.22 能力一致，18.20 与 18.17 却不一致），
 * 能力才是引擎真正依赖的东西。
 *
 * 用法：
 *   node runtime/probe.mjs            # 人类可读
 *   node runtime/probe.mjs --json     # 机器可读（给 Swift 侧解析）
 *   node runtime/probe.mjs --strict   # 缺必需能力则以 exit code 78 退出（EX_CONFIG）
 *
 * 设计约定：
 *   - FLOOR（必需）= 引擎不能跑的底线，缺一个就拒绝启动
 *   - NICE（可选）= 有则启用优化路径，无则走降级实现，不影响正确性
 *   - INFO（无关）= 仅记录，用于诊断与升级评估
 */
import fs from 'node:fs';
import { createRequire } from 'node:module';

const req = createRequire(import.meta.url);
const tryReq = (id) => {
  try { return req(id); } catch { return null; }
};

const REQUIRED = [];
const OPTIONAL = [];
const INFO = [];

const check = (bucket, name, minVer, fn) => {
  let ok = false;
  let err = null;
  try {
    ok = !!fn();
  } catch (e) {
    err = String(e && e.message ? e.message : e);
  }
  bucket.push({ name, minVer, ok, err });
};

/* ---------- FLOOR：引擎正确运行的最小集合 ---------- */

// 1) 同步 IO 全家族。引擎全部走同步路径：异步交给 IPC 层，存储层不要事件循环。
check(REQUIRED, 'fs.openSync/readSync/writeSync/closeSync', '0.10+', () =>
  ['openSync', 'readSync', 'writeSync', 'closeSync'].every((k) => typeof fs[k] === 'function'));

// 2) fsync / fdatasync。缺 fdatasync 可以退回 fsync，但缺 fsync 就等于放弃持久性保证。
check(REQUIRED, 'fs.fsyncSync', '0.10+', () => typeof fs.fsyncSync === 'function');

// 3) 原子替换与目录操作（清空 = rename；snapshot = rename 覆盖）
check(REQUIRED, 'fs.renameSync', '0.10+', () => typeof fs.renameSync === 'function');
check(REQUIRED, 'fs.mkdirSync/readdirSync/statSync', '0.10+', () =>
  ['mkdirSync', 'readdirSync', 'statSync', 'unlinkSync'].every((k) => typeof fs[k] === 'function'));

// 4) 带 position 的定位读写 —— 整个列存格式的基础。
//    实测假阳性风险：某些运行时接受 position 但忽略它，所以必须真读写验证。
check(REQUIRED, 'fs.readSync 支持 position 定位', '0.10+', () => {
  const p = `/tmp/_probe_${process.pid}.bin`;
  try {
    const fd = fs.openSync(p, 'w+');
    fs.writeSync(fd, Buffer.from([1, 2, 3, 4]), 0, 4, 0);
    const b = Buffer.allocUnsafe(2);
    const n = fs.readSync(fd, b, 0, 2, 2); // 从第 3 字节读 2 字节 → 应为 [3,4]
    fs.closeSync(fd);
    return n === 2 && b[0] === 3 && b[1] === 4;
  } finally {
    try { fs.unlinkSync(p); } catch {}
  }
});

// 5) Buffer 的定长整数编解码（列文件全靠它）
check(REQUIRED, 'Buffer 定长整数读写 (LE/BE, 8/16/32/64)', '5.10+', () => {
  const b = Buffer.allocUnsafe(16);
  b.writeUInt32LE(0xdeadbeef, 0);
  b.writeBigUInt64LE(9007199254740993n, 8);
  return b.readUInt32LE(0) === 0xdeadbeef && b.readBigUInt64LE(8) === 9007199254740993n;
});

// 6) TypedArray 零拷贝视图 —— 双倍收益：快（实测 4.60→1.92ms/百万行）+ 不进 V8 heap（不触发 GC）。
check(REQUIRED, 'TypedArray 视图可建立在 Buffer 之上', '4+', () => {
  const b = Buffer.allocUnsafe(64);
  const v = new Uint32Array(b.buffer, b.byteOffset, 16);
  v[3] = 0x01020304;
  return b.readUInt32LE(12) === 0x01020304 && v.byteOffset === b.byteOffset;
});

// 7) BigInt。seq / offset / 纳秒时间戳必须 64 位；Number 在 2^53 之后会静默丢精度。
check(REQUIRED, 'BigInt', '10.4+', () => typeof BigInt === 'function' && BigInt(2) ** 63n > 0);

// 8) 高精度计时，用于 group commit 的自适应窗口（ewma）
check(REQUIRED, 'process.hrtime.bigint', '10.7+', () => typeof process.hrtime.bigint === 'function');

// 9) 结构化克隆不需要，但 Buffer.from(arrayBuffer, offset, len) 需要（body 切片零拷贝）
check(REQUIRED, 'Buffer.from(arrayBuffer, byteOffset, length)', '5.10+', () => {
  const ab = new ArrayBuffer(16);
  new Uint8Array(ab)[5] = 42;
  return Buffer.from(ab, 5, 1)[0] === 42;
});

/* ---------- NICE：有则加速，无则降级 ---------- */

check(OPTIONAL, 'fs.rmSync（清空后台删除可简化）', '14.14+', () => typeof fs.rmSync === 'function');
check(OPTIONAL, 'worker_threads（后台 compaction / 压缩）', '12+', () => {
  const w = tryReq('node:worker_threads');
  return !!w && typeof w.Worker === 'function';
});
check(OPTIONAL, 'fs.cpSync + COPYFILE_FICLONE（APFS CoW 复制大 body）', '16.7+', () =>
  typeof fs.cpSync === 'function' && typeof fs.constants.COPYFILE_FICLONE === 'number');
check(OPTIONAL, 'zlib zstd（body 压缩，Node 22.15+）', '22.15+', () => {
  const z = tryReq('node:zlib');
  return !!z && typeof z.zstdCompressSync === 'function';
});
check(OPTIONAL, 'Array.prototype.at（仅代码风格，可避免）', '16.6+', () => typeof [].at === 'function');
check(OPTIONAL, 'structuredClone（仅测试用）', '17+', () => typeof globalThis.structuredClone === 'function');

/* ---------- INFO：只记录，不判定 ---------- */

INFO.push({ name: 'node', value: process.version });
INFO.push({ name: 'v8', value: process.versions.v8 });
INFO.push({ name: 'arch', value: process.arch });
INFO.push({ name: 'platform', value: `${process.platform} ${typeof process.getSystemVersion === 'function' ? process.getSystemVersion() : ''}`.trim() });
INFO.push({ name: 'icu', value: process.config?.variables?.icu_small ? 'small-icu' : 'full-or-none' });
// node:sqlite 只是记录：本方案不使用它，但要知道打包的运行时里它在不在
// （Stability 1.2，且 26.10/26.11 连续改过 undefined→NULL 绑定与 DatabaseSync→Database 重命名）
INFO.push({ name: 'node:sqlite', value: (() => {
  // 加载它会在 stderr 打 ExperimentalWarning，污染启动日志 —— 探测期间临时静音
  const origEmit = process.emitWarning;
  process.emitWarning = () => {};
  try { return tryReq('node:sqlite') ? 'present (unused by design)' : 'absent (irrelevant)'; }
  finally { process.emitWarning = origEmit; }
})() });

/* ---------- 输出 ---------- */

const missingRequired = REQUIRED.filter((c) => !c.ok);
const missingOptional = OPTIONAL.filter((c) => !c.ok);
const code = missingRequired.length === 0 ? 0 : 78; // 78 = EX_CONFIG

if (process.argv.includes('--json')) {
  process.stdout.write(JSON.stringify({
    ok: missingRequired.length === 0,
    node: process.version,
    required: REQUIRED,
    optional: OPTIONAL,
    info: INFO,
    missing_required: missingRequired.map((c) => c.name),
  }, null, 2) + '\n');
} else {
  const pad = (s, n) => (s + ' '.repeat(n)).slice(0, n);
  console.log(`运行时自检  node ${process.version}  ${process.arch}  ${process.platform}\n`);
  console.log('必需能力（缺一项即拒绝启动）');
  for (const c of REQUIRED) console.log(`  ${c.ok ? '✓' : '✗'} ${pad(c.name, 52)} ${c.minVer}`);
  console.log('\n可选能力（缺则走降级实现）');
  for (const c of OPTIONAL) console.log(`  ${c.ok ? '✓' : '·'} ${pad(c.name, 52)} ${c.minVer}`);
  console.log('\n环境');
  for (const i of INFO) console.log(`  · ${pad(i.name, 12)} ${i.value}`);
  if (missingRequired.length) {
    console.log(`\n[FATAL] 缺少 ${missingRequired.length} 项必需能力，存储层无法安全运行。`);
    console.log('        最可能原因：打包的运行时被替换成了过旧或裁剪过的 Node。');
  } else {
    console.log(`\n结论：可用。${missingOptional.length ? `缺 ${missingOptional.length} 项可选能力，将降级。` : '全部可选能力就绪。'}`);
  }
}

if (process.argv.includes('--strict')) process.exit(code);
```

2. **没有端到端数字**。所有性能都是微基准（合成数据、单线程、x64），§13 的十条验收全部「待测」。
3. **有 4 项空白 + 3 个待定输入**（§14），其中「敏感数据加密」是唯一可能迫使架构返工的一项 ——
   因为它决定 body 是否加密、密钥如何托管、清空与密钥轮换如何配合。

**结论：这是「可以开始实现的规格」，不是「已完成的方案」。**
